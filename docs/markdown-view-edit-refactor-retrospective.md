# Markdown 查看/编辑重构复盘与 1.0 稳定性约定

## 摘要

本次重构把笔记区从常驻的 Milkdown/Crepe WYSIWYG 编辑器改为“阅读优先、按需编辑”：
笔记默认由 `react-markdown` 与 `remark-gfm` 渲染，首次进入编辑态时才异步加载
CodeMirror 6。支持范围固定为 CommonMark、GFM 表格与任务列表、围栏代码；原始
HTML、数学公式、Mermaid 和语法高亮不属于 1.0 范围。

真正困难的部分不是替换渲染组件，而是在异步读取、400 ms 自动保存、手动保存、
切换文件、切换模式、失败重试和卸载同时发生时，仍保证内容不会写错路径、旧结果
不会覆盖新状态。最终实现以捕获的 `path/content/session/version/generation`
保存快照、按路径串行队列和可回收的路径水位为核心。失败重试快照与水位回收完成
后形成 85 项重构基线；长链接与源码视觉换行补入两项回归后，形成 87 项最终收尾
基线。

## 背景与目标

旧实现每次打开笔记都会创建 Milkdown/Crepe，适合 WYSIWYG 写作，却与本产品
“阅读多、编辑少”的主要使用方式不匹配。重构目标不是扩展富文本能力，而是减少
只读场景的运行时负担，同时保留可靠的 Markdown 源码编辑体验。

目标被收敛为四项：

1. 打开或切换笔记固定进入渲染查看态，查看时不初始化任何编辑器。
2. 通过 `Cmd/Ctrl + E` 或低强调按钮进入源码编辑，CodeMirror 仅在首次需要时
   加载；`Cmd/Ctrl + S` 在编辑态立即保存。
3. 保持既有 Notes 后端命令、绝对路径和 frontmatter 语义不变。
4. 将“不会丢内容、不会串文件”定义为比视觉切换更高优先级的正确性约束。

## 方案调研与取舍

查看态选择 `react-markdown + remark-gfm`，因为它与 React 组件模型直接衔接，
默认不执行原始 HTML，且能以组件映射定制表格、链接、图片、代码与只读任务项。
`marked + DOMPurify` 和 `markdown-it` 都会引入 HTML 字符串与额外安全边界；
直接使用 `micromark` 会重复搭建 AST 到 React 的转换链；Rust 后端解析则为普通
单篇笔记增加了没有证据支持的 IPC 复杂度。

编辑态选择已有直接依赖的 CodeMirror 6，而不是继续维护 Crepe，也没有退化到
原生 `textarea`。CodeMirror 能提供搜索、撤销、选区、缩进和长文档编辑能力，
并可通过动态导入隔离出查看首屏。Monaco 的体积、Worker 与初始化成本超过单篇
Markdown 源码编辑所需。

排版采用 Tailwind Typography 加少量产品样式覆盖。围栏代码保留语言 class，
但 1.0 不引入 Shiki、Prism 或 highlight.js：当前没有证据证明高亮收益足以抵消
语言包、主题和 DOM 转换成本。

Yjs 没有引入，因为当前是本地单文档、单用户编辑，不存在协同 CRDT 问题；RxJS
没有引入，因为保存时序可由局部 hook、Promise 与按路径队列清晰表达；Zustand
没有引入，因为文档内容只有一个 session owner，共享全局 store 反而会扩大跨文件
状态污染面。三者都不是能力不足，而是问题规模尚未达到引入它们的阈值。

迁移完成后移除了 Milkdown/Crepe、只为旧编辑器存在的运行时代码、样式和孤立
依赖。该决策同时避免保留两套编辑模型造成维护分叉。

## 最终架构

`NotesPanel` 继续只把 `filePath` 交给右侧的 `NoteEditor`，对外接口没有扩大。
内部职责分为：

- `NoteEditor`：薄控制器，拥有查看/编辑模式、快捷键、模式切换和位置快照；
- `useNoteDocument`：唯一文档内容 owner，负责读取、版本、脏状态、自动保存、
  flush、失败重试与跨 session 隔离；
- `MarkdownViewer`：渲染 CommonMark/GFM，不读写文件；
- `MarkdownSourceEditor`：按需加载并封装 CodeMirror，不保存文件；
- `NoteSaveQueue`：同一路径严格串行，不同路径互不阻塞。

查看态和编辑态消费同一份内存内容，成功退出编辑态无需重新读盘。选择新文件时
界面立即回到查看态与加载态，不会把旧笔记正文暂时显示在新选择之下。CodeMirror
首次异步加载后聚焦；同一文件 session 内分别保存查看滚动位置、编辑滚动位置和
选区，切换文件时丢弃这些临时 UI 状态。

## 读取与保存竞态：问题、失败路径与不变量

早期设计只要覆盖“防抖时捕获旧路径”仍不够。真实失败路径还包括：A 的保存未完成
便切到 B、A 的旧读取晚于 B 返回、保存等待期间继续输入、同一路径被重新打开、
旧失败晚于新成功返回、失败重试与新提交重叠，以及页面卸载时定时器尚未触发。

最终保存提交捕获 `path`、`content`、`session`、`version`，并在同一存活的
watermark epoch 内为每条路径分配单调递增的 `generation`。这些字段共同标识一次
不可变保存快照，不能在 Promise 完成时回读“当前”变量。实现遵守以下不变量：

1. **旧读取不得提交。** 读取结果只有在捕获的 path 与 session 仍是当前值时才能
   更新界面；读取前先等待该路径已有写入的 `pending(path)`，避免刚保存后立即
   读到旧磁盘内容。路径水位同时记录 pending reads。
2. **写入不得串路径。** 所有写入携带捕获路径进入共享队列；同一路径严格串行，
   不同路径可以并行。文件切换不等待旧路径写完，但会先提交旧 session 的最新
   脏快照。
3. **旧完成不得宣布新内容已保存。** 只有 path、session、version 和 content
   仍与活动快照一致时，成功结果才能清除 dirty 并显示 saved；旧写入成功只能
   推进队列。
4. **空字符串是有效内容。** 是否保存由版本与 dirty 决定，不能用内容 truthiness
   判断，因此清空整篇笔记仍会写入。
5. **flush 必须排空而非只等一次。** flush 在等待期间若发现版本继续增长，会再次
   捕获并提交，直到观察到稳定版本；退出编辑态只有在最新快照成功后才进入查看态。
6. **失败必须可恢复。** 最新未被同一 watermark epoch 内后续 generation 取代的
   失败会保留完整快照。活动且已继续编辑的 session 重试最新内容；旧文件失败则
   重试原捕获内容。同一 epoch 内更新的 generation 不会被较旧失败覆盖，重试成功
   才清除错误。
7. **卸载仍要提交。** 文件切换和组件 cleanup 都取消防抖定时器并 flush 当前
   快照；异步失败发生在卸载后时，1.0 以控制台报告作为最后兜底，不再写已卸载
   React 状态。
8. **水位必须可回收。** 每路径 watermark 跟踪未完成提交数、pending reads、
   最新 generation 和最新 Promise；只有在没有 submission、read、failure 或
   retry 的完全静默状态下才能回收。之后同一路径创建的是新 epoch，generation
   可以从初始值重新开始，因此 generation 只在所属 epoch 内比较。回收还必须检查
   Map 中对象仍是回调捕获的 watermark，防止旧 callback 删除同路径的新 epoch。

这些规则把“保存成功”从一个 Promise 是否 resolve，提升为“resolve 的快照是否
仍有资格改变当前状态”，也是本次重构最重要的维护边界。

## 测试、审查与真实桌面验收

自动化测试覆盖 viewer 语义与安全、CodeMirror 适配、控制器交互、按路径保存队列
及文档 session 竞态。失败重试快照与 watermark 回收完成后，重构基线为 85 项
测试；提交 `f30f0f7` 再加入 rendered link wrapping 与 CodeMirror
`lineWrapping` 两项回归，形成 87 项最终收尾基线。最终行为是：长链接在阅读列内
换行；源码编辑器只做视觉换行，不插入换行符或改变 Markdown 文本；围栏代码仍在
代码块内横向滚动。生产构建还验证了 CodeMirror 位于异步 chunk、查看路径不包含
Milkdown/ProseMirror，且没有语法高亮包。

jsdom 无法证明真实布局、IME 和编辑器手感，因此这些项目在真实 macOS Tauri
桌面应用中验收。结果如下：

- 深色主题随系统主题生效，查看与编辑的正文、边框和代码区域均保持可读；
- 中文 IME 组合输入正常，没有中间组合文本回写或内容回声；
- 窄窗口下正文与工具栏保持可用，长链接在阅读列内换行，表格和围栏代码在各自
  容器内横向滚动；源码长行只视觉换行，不改变底层 Markdown；
- 查看态与编辑态的滚动位置分开恢复，同一 session 的编辑选区可恢复；
- 清空整篇笔记可以保存为空内容，重新读取不会恢复旧正文；
- 人为触发保存失败时保留编辑内容和编辑态，重试后可恢复；旧文件后台失败会带
  路径展示，不会替换当前笔记；
- 编辑中快速 A/B 选择时，迟到读取不会覆盖当前内容，保存不会跨路径，A 与 B
  保持隔离。

审查重点放在竞态不变量，而不是仅检查正常路径。后续修复过 flush 等待期间继续
输入、卸载后状态更新、同路径重开、旧失败覆盖新结果和重试快照被后续 session
误替换等边界，说明异步正确性必须通过可控 Promise 与反序完成顺序来验证。

## 最终结果

1. 笔记默认以排版后的 Markdown 打开，编辑器成本从阅读路径移出。
2. `Cmd/Ctrl + E` 与按钮提供一致的查看/源码编辑切换，首次编辑才加载 CodeMirror。
3. CommonMark、GFM 表格、任务列表和围栏代码形成明确的 1.0 渲染边界。
4. Milkdown/Crepe 及其专属配置被移除，架构文档已改为当前组件与保存链路。
5. 空保存、失败重试、快速切换和卸载 flush 都纳入同一套版本化保存语义。
6. 没有为未出现的协同、全局状态或流式编排需求引入 Yjs、Zustand 或 RxJS。

本次没有记录毫秒级性能提升或 bundle 减少比例，因为没有可靠、可复现的测量
数据；结论只限于可验证的加载边界、行为与测试结果。

## 做得好的地方

- 先固定产品边界，再选库。CommonMark/GFM 与“不做高亮”让安全、样式和依赖
  决策都有清晰依据。
- 复用既有按路径保存队列，并把复杂度集中在唯一内容 owner 中，没有用全局状态
  或通用状态机扩散问题。
- 测试不仅覆盖成功路径，还主动控制读取和写入完成顺序，暴露了真实竞态。
- 把 CodeMirror 适配、viewer 与 session hook 分开，使 DOM 语义、编辑器生命周期
  和持久化顺序可以独立审查。
- 真实桌面验收补足了 jsdom 无法覆盖的主题、IME、滚动、选区和窄窗口行为。

## 可以改进的地方

- 最初的保存模型偏重 path/session/version，较晚才把每路径 generation、pending
  reads 与可回收水位纳入同一模型。设计阶段若先列出所有“迟到完成”组合，可减少
  后期修复波次。
- “flush”一开始容易被理解为等待当前 Promise，而不是持续排空至稳定版本。接口
  命名或契约应更早明确 drain 语义。
- 卸载、同路径重开和失败后继续编辑应从首轮测试矩阵开始就是一等场景，而不是
  正常切换完成后的补充项。
- 自动化证据与真实桌面验收应直接沉淀到持久文档；临时执行报告可以辅助交接，
  但不应成为未来维护者必须依赖的事实源。
- 未来若要讨论性能，应先固定短、典型、长笔记样本和测量方法，再给出数据，不能
  用“异步 chunk”替代实际性能指标。

## 已知技术债

- 生产构建仍有既存的 sourcemap location 警告。它没有阻断构建，也没有证据表明
  会改变 1.0 运行时行为，暂列为非阻塞构建债务。
- 生产构建仍有 large-chunk 警告。CodeMirror 已被隔离到异步 chunk，但其他
  chunk 的拆分与阈值调整需要基于真实加载数据，不能只为消除警告改配置。
- Notes 页面卸载后才到达的后台保存失败只能记录到控制台；若未来需要跨页面持续
  可见，应另行设计应用级通知/任务中心，而不是把全局机制塞回文档 hook。
- 尚无经过固定样本重复测量的启动、首次查看和首次编辑耗时。本复盘不把缺失数据
  包装成性能结论。
- 1.0 不提供像素级查看/编辑同步滚动、跨重启选区恢复、语法高亮或高级 Markdown
  扩展；这些是明确的非目标，不是当前发布阻塞项。

## 1.0.0 之后的维护约定

`1.0.0` 之后采用兼容性优先策略。默认查看态、按需 CodeMirror、现有快捷键、
CommonMark/GFM 支持范围、原始 HTML 禁用、400 ms 自动保存、空内容可保存、
按路径串行和失败可重试共同构成稳定维护契约。

维护规则如下：

1. 补丁与次版本不得静默改变上述可观察行为；必须改变时，应先给出迁移说明，并按
   语义化版本判断是否属于 breaking change、需要主版本。
2. 修改 `useNoteDocument` 或保存队列前，必须保留 path/session/version/generation
   快照资格判断、pending-read 屏障、flush drain、卸载 flush、重试保留和水位回收。
   不能用“最后一次 Promise”或全局 loading 布尔值替代这些不变量。
3. 升级 Markdown 解析依赖时，必须复查 CommonMark/GFM 输出、危险 URL、原始 HTML、
   只读任务项和外部链接策略；新增扩展默认关闭，除非有独立设计与兼容测试。
4. 升级 CodeMirror 时，必须确认它仍按需加载，主题更新不重建文档，IME、选区、
   滚动、搜索和焦点行为不回退。
5. 现有设置格式与笔记存储契约不得在普通维护中随意改变，包括 Notes 后端命令、
   绝对路径和 frontmatter 语义。migration 或 deprecation 必须独立设计，保护用户
   数据，提供可恢复或可回退路径，并确保中途失败不会留下无法读取的数据。
6. 发布偏好小型、可审查、可回退的增量；不要在同一发布中混合无关的存储迁移、
   解析器变更和保存并发调整，回退也不得使新旧数据任一侧失去可读性。
7. 不因“可能以后需要”引入 Yjs、RxJS、Zustand、Monaco、高亮器或解析缓存。只有
   真实需求和测量表明现架构不足时，才重新选型。
8. 构建警告应记录和评估，但不得通过掩盖警告或任意提高阈值冒充修复。

## 给未来维护者的检查清单

- [ ] 新笔记和切换后的笔记是否始终先进入查看态，且查看时未初始化 CodeMirror？
- [ ] CommonMark、GFM 表格、只读任务列表和围栏代码是否仍按 1.0 范围渲染？
- [ ] 原始 HTML 与危险 URL 是否仍不会变成可执行内容？
- [ ] `Cmd/Ctrl + E`、按钮和编辑态 `Cmd/Ctrl + S` 是否保持一致语义？
- [ ] 保存是否捕获完整的 path/content/session/version/generation，而非读取可变当前值？
- [ ] 旧读取是否同时受 path/session 检查与同路径 pending-write 屏障保护？
- [ ] 同路径写入是否串行，不同路径是否互不阻塞，空字符串是否仍会写入？
- [ ] flush 是否在等待期间继续输入时排空至稳定版本，失败时是否留在编辑态？
- [ ] 失败快照是否可重试，同一 watermark epoch 内旧 generation 是否无法覆盖新结果？
- [ ] 文件切换和卸载是否取消 timer 并提交最新脏快照？
- [ ] generation 是否只在同一存活 watermark epoch 内比较，新 epoch 是否允许重启？
- [ ] watermark 是否仅在完全静默时回收，对象身份检查是否能挡住旧 callback？
- [ ] 快速 A/B 切换、同路径重开和反序 Promise 完成是否都有回归测试？
- [ ] 深色主题、中文 IME、窄窗口、横向滚动、选区与独立滚动位置是否在真实桌面复验？
- [ ] 长链接是否在阅读列内换行，源码是否只视觉换行，围栏代码是否仍横向滚动？
- [ ] CodeMirror 是否仍位于异步 chunk，Milkdown/Crepe 与语法高亮依赖是否未回流？
- [ ] 设置格式或笔记存储若变更，migration/deprecation 是否保护数据且可恢复？
- [ ] 发布是否保持小型、可审查、可回退，且 breaking change 已正确标记？
- [ ] 构建中的 sourcemap location 与 large-chunk 警告是否被重新评估并如实记录？
- [ ] 任何性能结论是否来自固定样本和可复现测量，而不是主观感受？
